# 서부산 숙박시설 데이터 파이프라인 및 분석 설계

## 1. 목적

부산의 합법 숙박시설 공급, 규모, 건축 노후도, 관광객 수요와 교통 유입을 지속적으로 수집·결합하여 서부산의 숙박여건을 동부산 및 부산 기타지역과 비교한다. 분석은 다음 정책 판단을 지원한다.

- 서부산 숙박시설의 영세성과 건축 노후도가 실제로 더 높은가.
- 관광객과 교통 유입에 비해 객실 및 관광숙박 공급이 부족한가.
- 신규 공급, 시설개선, 관광콘텐츠 연계 중 어떤 지원이 우선인가.

결론을 사전에 고정하지 않는다. 동일한 지표와 품질기준을 세 권역에 적용하고, 결과 조합에 따라 정책방향을 판정한다.

## 2. 구축 범위와 원칙

### 2.1 초기 구축 범위

- 실행환경: Windows 로컬 PC
- 처리언어: Python
- 분석 데이터베이스: DuckDB
- 원본 보존: 날짜별 JSON 및 Parquet
- 시계열 소급수집 우선범위: 각 소스가 지원하는 2022년 1월부터 현재까지
- 확장 소급기간: API가 더 오래된 자료를 제공하고 호출한도가 허용하면 제공 가능한 전 기간
- 현재상태만 제공하는 인허가·대장 소스: 최초 전수 스냅샷 이후 일일 관찰이력을 자체 축적
- 갱신: 매일 실행하되 자료의 실제 발표주기에 맞춰 신규자료 여부 확인
- 대시보드: 이번 구현 범위에서 제외하되 분석용 뷰를 제공

### 2.2 설계 원칙

1. 원본, 표준화, 분석 계층을 분리한다.
2. 원본 응답과 요청조건을 보존해 동일 결과를 재현할 수 있게 한다.
3. 숙박시설과 법적 인허가·등록을 분리해 이중등록을 중복 시설로 집계하지 않는다.
4. 실제 점유율, OTA 판매압력, 공공데이터 기반 수요압력을 서로 다른 지표로 취급한다.
5. 결측·지연·추정값에는 품질등급과 근거를 붙인다.
6. 로컬 저장 기술이 바뀌어도 수집·정제·분석 규칙을 재사용할 수 있게 한다.

## 3. 권역 정의

| 권역 | 구·군 |
| --- | --- |
| 서부산 | 강서구, 북구, 사상구, 사하구 |
| 동부산 | 해운대구, 수영구, 기장군 |
| 부산 기타지역 | 중구, 서구, 동구, 영도구, 부산진구, 동래구, 남구, 금정구, 연제구 |

모든 분석결과는 권역 단위와 16개 구·군 단위를 함께 저장한다. 주소 정규화에 실패하거나 부산 권역으로 분류되지 않는 레코드는 분석에서 조용히 제외하지 않고 품질검토 테이블에 보낸다.

ODCloud 자료는 게시 때마다 UDDI가 바뀔 수 있으므로 특정 UDDI를 영구 고정하지 않는다. namespace의 OpenAPI 문서 또는 데이터 목록에서 최신 게시물의 식별자를 발견하고, 발견된 식별자·게시일·행 수를 수집 이력에 기록한다.

한국철도공사 파일자료는 특정 조사기간의 보조자료이며 일일 모니터링 자료로 오인하지 않는다. 신청하지 않은 열차종별 발권자료와 시외버스 스케줄 API는 초기 범위에서 제외한다.

## 5. 데이터 계층과 저장구조

### 5.1 원본 계층

경로 규칙은 `data/raw/{source_id}/ingest_date=YYYY-MM-DD/`로 한다. 각 요청에 대해 다음 메타데이터를 저장한다.

- `run_id`, `source_id`, 요청시각, 기준기간
- URL에서 인증값을 제거한 요청조건
- 페이지 번호와 페이지 크기
- HTTP 상태, 응답 헤더, 응답 행 수
- 응답 파일 해시와 스키마 지문
- 원본 기준일과 게시일

원본 파일은 같은 요청 해시와 같은 응답 해시가 이미 있으면 다시 쓰지 않는다.

### 5.2 표준화 계층

DuckDB의 표준화 테이블은 다음 공통 필드를 가진다.

- 원본 출처와 원본 레코드 식별자
- 최초·최근 관찰일
- 법적 업종과 세부업종
- 영업상태, 인허가일, 폐업일
- 원본 주소, 정규화 도로명주소, 정규화 지번주소
- 행정구역코드, 권역코드
- 시설명·전화번호 정규화값
- 객실 수 및 객실 수 품질상태
- 좌표, 건축물 키, 필지 키
- 레코드 품질등급과 제외사유

### 5.3 분석 계층

주요 분석 테이블과 뷰는 다음과 같다.

- `dim_region`: 부산 16개 구·군과 권역
- `dim_facility`: 중복 제거된 실제 숙박시설
- `fact_license_snapshot`: 날짜별 법적 인허가·등록 상태
- `bridge_facility_license`: 실제 시설과 복수 법적 등록 관계
- `dim_building`: 건축물대장 기준 건축물
- `bridge_facility_building`: 시설과 건축물 관계
- `fact_building_event`: 신축·증축·대수선·용도변경·폐쇄말소
- `fact_tourism_demand`: 월·지역별 방문·체류·소비
- `fact_transport_flow`: 월·지역·교통수단별 이동량
- `fact_data_quality`: 실행·소스·테이블별 품질검사 결과
- `mart_region_month`: 구·군 및 권역별 월간 분석지표
- `mart_facility_current`: 시설별 최신 통합현황
- `mart_duplicate_review`: 사람이 확인할 유력 중복 후보

## 6. 숙박시설 중복통합

### 6.1 기본 모델

하나의 실제 숙박시설에 공중위생법상 숙박업 인허가, 관광진흥법상 관광숙박업 등록, 관광펜션 지정 등 여러 법적 레코드가 연결될 수 있다. 실제 시설 수는 `dim_facility`를 집계하고, 법적 업종별 건수는 `fact_license_snapshot`을 집계한다.

원본 레코드는 삭제하거나 덮어쓰지 않는다. 통합 판단과 판단 근거, 알고리즘 버전, 검토상태를 별도 기록한다.

### 6.2 정규화

- 시설명: 법인표기, 공백, 특수문자, 지점 접미어를 표준화하되 원문 보존
- 주소: 도로명·지번·건물 본번·부번·동·층·호 분리
- 전화번호: 숫자형 표준화
- 업종: 원본 분류와 공통 분류를 모두 보존
- 좌표: 동일 좌표계로 변환

### 6.3 판정 단계

1. 동일 원본 내 공식 인허가·관리번호 중복은 동일 등록으로 통합한다.
2. 서로 다른 법적 소스 간에는 건축물 키, 필지 키, 정규화 주소, 시설명, 전화번호, 좌표를 조합한다.
3. 명확한 공식 식별자 일치 또는 검증된 고정밀 규칙만 자동 통합한다.
4. 주소와 명칭이 유사하지만 확정할 수 없는 경우 `유력 중복`으로 보낸다.
5. 같은 주소라도 명칭·전화·인허가가 다른 업체는 별도 시설로 유지한다.

자동통합 규칙은 사람이 라벨링한 후보 표본에서 정밀도 99% 이상을 충족해야 활성화한다. 재현율보다 오통합 방지를 우선한다. 유력 중복은 분석에서 임의로 합치지 않고 검토 전·후 건수를 함께 관리한다.

### 6.4 대표 분류

한 시설에 일반숙박과 관광숙박 등록이 모두 있으면 시설 수는 한 번만 센다. 대표 분석분류는 관광숙박 세부업종을 우선하되 다음 속성을 동시에 보존한다.

- `has_public_hygiene_license`
- `has_tourism_registration`
- `has_foreigner_homestay_registration`
- `has_rural_homestay_registration`
- `has_hanok_experience_registration`
- `has_tourist_pension_designation`

## 7. 분석지표

### 7.1 영세성

- 업체당 평균 객실 수 = 총 객실 수 / 객실 수 확인 시설 수
- 객실 수 중앙값과 사분위수
- 소규모 시설 비율 = 객실 수가 설정기준 이하인 시설 / 객실 수 확인 시설
- 대형 시설 객실 비중
- 관광숙박 시설 및 객실 비율

소규모 기준의 초기값은 20실이며 설정값으로 관리한다. 객실 수 결측률을 항상 함께 표시하고, 결측이 많은 업종의 값을 전체 시설로 확대해석하지 않는다.

### 7.2 건축 노후도

- 건축연령 = 분석 기준연도 - 사용승인연도
- 시설 기준 평균·중앙 건축연령
- 객실 가중 평균 건축연령
- 20년 이상, 30년 이상 건축물의 시설·객실 비율
- 최근 5년 증축·대수선·용도변경 시설 비율
- 건축물 폐쇄·말소 및 숙박업 폐업 추이

### 7.3 수급여건

- 객실 100실당 체류방문자 수
- 객실당 숙박소비액
- 인구 1만 명당 숙박시설·객실 수
- 방문객 증가율과 객실 증가율의 격차
- 교통 유입량 대비 숙박시설·객실 수
- 신규 인허가, 폐업, 순증감률

방문자·교통량을 객실점유율로 부르지 않는다. 이 지표들은 `숙박수요 압력` 또는 `수급여건`으로 표시한다.

### 7.4 관광수용성

- 관광숙박 객실 비율
- 외국인관광도시민박업 등 외국인 수용업종 비율
- 대형 숙박시설 비율
- 체류형 관광수요 대비 관광숙박 객실 수
- 내국인·외국인 관련 수요지표가 제공될 경우 각각의 객실 대비 비율

### 7.5 향후 보강지표

- 공식 객실점유율·ADR·RevPAR: 확보된 관광호텔 범위에만 적용
- OTA 가격·예약가능률·후기·온라인 노출률: 정식 API 또는 데이터 계약이 허용하는 범위에만 적용

OTA 예약가능률은 실제 객실점유율과 분리하고 `OTA 판매압력`으로 표시한다.

## 8. 정책 판정 규칙

| 관측 조합 | 우선 검토 정책 |
| --- | --- |
| 노후도 높음 + 영세성 높음 | 시설개선·리모델링 지원 |
| 수요압력 높음 + 객실 공급 부족 | 신규 관광숙박 공급 및 투자유치 |
| 수요 증가 + 관광숙박 비중 낮음 | 국내외 관광객 수용 인프라 확충 |
| 노후도 높음 + 수요압력 낮음 | 신규 공급보다 시설개선·콘텐츠 연계 |
| 폐업 증가 + 신규 인허가 부진 | 금융·규제개선·민간투자 지원 |

각 판단은 서부산과 동부산의 단일 평균 차이만으로 내리지 않는다. 구·군 분포, 중앙값, 최근 추세, 객실 가중값, 결측률을 함께 검토한다.

## 9. 실행 흐름

1. 소스 등록부에서 실행대상과 최신 성공 기준일을 읽는다.
2. 승인상태와 API 응답을 소량 호출로 확인한다.
3. 최초 실행은 소스가 과거 기준기간 조회를 지원하면 가용 전 기간을 페이지 단위로 소급수집하고, 현재상태만 제공하면 전수 스냅샷을 저장한다.
4. 이후 실행은 신규 기준기간 또는 변경 스냅샷만 수집한다.
5. 응답 원문을 임시파일에 쓴 뒤 해시검증 후 원본 경로로 원자적 이동한다.
6. 스키마와 기본 품질검사를 통과한 원본만 표준화한다.
7. 주소·업종·지역을 정규화하고 시설·인허가·건축물을 연결한다.
8. 중복통합과 품질검사를 실행한다.
9. 월·권역·구군 분석지표를 계산한다.
10. 전체 필수검사를 통과한 실행만 최신 분석버전으로 승격한다.

매일 실행하되 월별·비정기 자료는 게시일과 데이터 기준일을 확인해 신규자료가 있을 때만 내려받는다. 로컬 PC가 꺼져 실행하지 못한 기간은 다음 실행에서 마지막 성공 기준일 이후부터 보충한다.

## 10. 멱등성과 이력

- 모든 실행에 `run_id`를 부여한다.
- 요청조건을 정렬·정규화한 뒤 `request_hash`를 만든다.
- 원본 응답에 `content_hash`를 만든다.
- 동일 요청·동일 내용은 중복 저장하지 않는다.
- 스냅샷은 관찰일을 보존하고 최신상태만 별도 뷰로 제공한다.
- 정제 및 중복통합 알고리즘 버전을 결과에 기록한다.
- 과거 원본을 새 규칙으로 재처리할 수 있게 한다.

## 11. 오류처리와 복구

- 네트워크·일시적 서버 오류: 지수형 지연과 제한된 횟수로 재시도
- 인증·활용승인 오류: 즉시 해당 소스를 실패 처리하고 인증값을 로그에서 마스킹
- 호출한도 초과: 제공된 재시도 시각 또는 다음 실행으로 이월
- 페이지 중간 실패: 성공한 마지막 페이지 체크포인트부터 재개
- 응답 스키마 변경: 원본은 보존하되 해당 소스의 표준화·게시를 중단
- 일부 소스 실패: 이전 정상 분석버전을 유지하고 부분 결과를 최신으로 승격하지 않음
- 파일자료 변경: 파일 해시와 게시일을 비교하고 새 버전으로 보존

## 12. 데이터 품질기준

- 동일 인허가·관리번호 중복률

## 14. 보안과 운영

- 인증키는 `.env` 또는 운영체제 비밀저장소에서 읽는다.
- `.env`, 원본 민감정보, 실행로그의 인증값은 Git에서 제외한다.
- URL 로그에서 인증키와 토큰을 마스킹한다.
- 공개자료라도 전화번호 등 업체 연락정보는 대시보드 공개범위와 분리한다.
- 로컬 스케줄은 Windows 작업 스케줄러용 실행명령을 제공한다.
- 로그, 품질보고서, 최신 성공일을 한 위치에서 확인할 수 있게 한다.

## 15. PostgreSQL·클라우드 이전

DuckDB 전용 SQL을 최소화하고 데이터 접근 계층을 분리한다. 클라우드 이전 시 다음만 교체하는 것을 목표로 한다.

- DuckDB 분석 테이블을 PostgreSQL 테이블로 이전
- 로컬 원본 경로를 오브젝트 스토리지로 이전
- Windows 작업 스케줄러를 Cron 또는 관리형 스케줄러로 이전
- `.env`를 서버 비밀관리 서비스로 이전
- 로컬 로그를 중앙 로그·모니터링으로 이전

원본 파일 규격, 표준화 규칙, 시설 통합 규칙, KPI 계산식, 품질검사는 그대로 재사용한다.
